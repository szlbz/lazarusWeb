# 插件部署目录与动态探测指南（进程级插件）

适用范围：向导"插件模式"生成的工程，以及 `demos/pluginsDemo`。
旧的同进程 `lwmodules.pas` 方案不在本文范围（见 `docs/插件使用说明.md`）。

**最容易踩的坑**：demo 与向导新工程的"清单根目录"不是同一个位置。
两者的 `common/upluginproc.pas` 是**两份独立源码副本**，`ExeRoot` 实现不同。
部署前必须先确认用的是哪一套，否则清单放错层会"一个插件都发现不了"，
且日志没有任何异常。

## 1. 两套目录层次（必须分清）

动态探测的统一逻辑是：

```
ExeRoot()  →  GRoot
             ↓ 只扫 GRoot 的直接子目录（不递归）
             GRoot/<任意子目录>/*.plugin.ini
             ↓
             .run 运行副本 = GRoot/.run/<插件 exe 文件名>
```

差异只在 `ExeRoot()` 怎么从"宿主 exe 路径"推出 `GRoot`。

### 1.1 demos/pluginsDemo（宿主放在 `host\` 子目录）

宿主的 `ExeRoot` = `ExtractFileDir(宿主 exe 目录)`，即**宿主 exe 所在目录的父目录**。

```
pluginsDemo/                  ← GRoot = host 的父目录
  host/
    pluginsdemo(.exe)         ← 宿主 exe
    pluginsdemo.ini
    lw/                       ← 宿主静态资源
  dashplug/
    dashplug.plugin.ini       ← 清单（GRoot 的直接子目录里）
    dashplug(.exe) / dashplug.ini
  notesplug/
    notesplug.plugin.ini
    notesplug(.exe) / notesplug.ini
  reportsplug/
    reportsplug.plugin.ini
    reportsplug(.exe) / reportsplug.ini
  icons/                      ← 菜单图标（清单里 icon= 引用）
  .run/                       ← 运行期自动生成：插件 exe/ini 副本
```

宿主启动日志形如 `[pluginsDemo] 从 /home/lbz/pluginsDemo 发现插件 3 个`。
把清单放到 `host/` 里面，或放到更深一层子目录，都扫不到。

### 1.2 向导生成的插件工程（宿主在工程根目录）

模板里的 `ExeRoot` = `<宿主 exe 所在目录>/plugins`，即**宿主 exe 旁边固定名字的
`plugins` 子目录**。

```
<工程根>/                     ← 宿主 exe 所在目录
  <Name>.exe                  ← 宿主 exe
  <Name>.ini
  lw/                         ← 客户端静态资源
  common/                     ← 源码（运行不需要）
  plugins/                    ← GRoot = <宿主 exe 目录>\plugins
    hello/
      hello.plugin.ini        ← 清单
      hello(.exe) / hello.ini
    .run/                     ← 运行副本：plugins\.run\<exe 文件名>
```

判断方法：看日志里"从 … 发现插件 N 个"打印的 `GRoot` 是什么，
或看当前用的 `common/upluginproc.pas` 里 `ExeRoot` 函数：
`Result := ExtractFileDir(exeDir)` 是 demo 版；
`Result := IncludeTrailingPathDelimiter(exeDir) + 'plugins'` 是向导版。

## 2. 动态探测与拉起流程

```
PlugDiscover / PlugRescan
  ├─ GRoot := ExeRoot
  ├─ FindFirst(GRoot + '*')               只扫一层子目录
  │    └─ 每个子目录 FindFirst('*.plugin.ini')   文件名排序，同名 name 只认第一个
  ├─ ParseManifest: 读 name/title/group/icon/exe/port/roles
  │    ├─ name 合法字符 a-zA-Z0-9 .-_，最长 64；port 必填且 > 0
  │    ├─ exe 相对清单所在目录（绝对路径直接用）
  │    ├─ icon 相对清单所在目录，不存在 → 警告并忽略图标
  │    └─ UNIX：同目录若有同名的无后缀文件，优先用它（见 §5）
  ├─ 注册 /p/<name>/ 代理到 127.0.0.1:<port>
  └─ 菜单按 group 拆 '/' 建多级分组，title/icon 来自清单
StartOne（首次启动 / 重扫变更 / 热更新都走这里）
  ├─ ForceDirectories(GRoot + '.run')
  ├─ CopyFileRaw(原始 exe → .run/<exe 文件名>)，UNIX 上复制后 fpChmod 755
  ├─ CopyFileRaw(原始 ini → .run/<同名 ini>)
  ├─ TProcess 拉起，带 --port= 和守卫三参数
  └─ 轮询端口直到可连接（最多 10s），日志"插件 X 端口 N 已就绪"
```

`PlugRescan`（菜单上的"重新扫描插件"）做"磁盘 → 运行时"对齐：
新增目录加入并拉起，消失的停进程 + 摘路由 + 关页签，端口/exe 变了的重启，
标题/分组/图标就地更新。

## 3. 清单文件（*.plugin.ini）

样例（demo 的便签插件）：

```ini
name=notes                  ; 路由名，访问 /p/notes/，必须唯一
title=便签                  ; 菜单文字，缺省 = name
group=系统管理/数据维护       ; 菜单分组，/ 表示层级；缺省「插件」
icon=..\icons\notes.bmp     ; 相对清单目录，16x16 bmp/png，可省略
exe=notesplug.exe           ; 相对清单目录；缺省 = <清单名去 .plugin.ini>.exe
port=8882                   ; 必填，插件进程监听端口
roles=admin,analyst         ; 允许访问的角色，逗号分隔；空 = 所有已登录用户
```

| 字段 | 要点 |
| --- | --- |
| `name` | 决定 `/p/<name>/`、菜单 Tag；重复时按文件名排序取第一个，后面的静默忽略 |
| `group` | 不写 = 默认「插件」；`group=-` = 插件直接作为顶层菜单行；`A/B/C` 任意层 |
| `icon` | 路径相对清单目录；Linux 部署时用 `/`，或在清单里写相对路径并上传图标文件 |
| `exe` | 路径相对清单目录；不同插件**不要用同一个 exe 文件名**，否则 `.run` 里会互相覆盖 |
| `port` | 宿主与插件各方端口不能冲突；改端口后重新扫描会重启该插件 |
| `roles` | 权限判定在宿主代理层；`admin` 通配全部；空 = 所有已登录用户 |

## 4. 部署检查清单

- [ ] 宿主 exe + 宿主 `.ini` 在同目录；确认宿主的 `ExeRoot` 属于 §1 的哪一套。
- [ ] 每个插件**一个直接子目录**，目录里有 `*.plugin.ini` + 插件 exe + 同名 `.ini`。
- [ ] 清单里的 `exe=` 指向的文件确实存在（Linux 允许写 `xxx.exe` 而实际是
      无后缀 ELF，见 §5）。
- [ ] 图标目录存在且 `icon=` 能解析；缺失只影响菜单外观，不影响功能。
- [ ] 静态资源：经宿主 `/p/` 代理时 `/lw/*` 由宿主直出；独立直连插件端口调试
      时，插件 exe 同目录要有 `lw/`。旧构建的插件需要在 `.run/lw/` 放一份，
      否则页面白屏并出现"未找到 alpine.min.js / lw.js"告警。
- [ ] `.run/` 无需预建、也不要提交；宿主每次启动自动重建副本。
- [ ] 被强杀后有残留进程时用 `stop-all.bat` / `bash stop-all.sh` 清理
      （按 exe 真实路径过滤，不会误杀其它 demo）。

## 5. Linux / aarch64 部署要点

1. **运行副本必须可执行。** 宿主把插件复制到 `.run` 后用 `fpChmod(Dst, &755)`
   补执行位（已做进框架向导模板和 demo；FPC/Linux 上 `FileSetAttr` 实测无效）。
   如果仍看到退出码 127，先查 `.run/<插件>` 的权限是不是 `-rwxr-xr-x`。
2. **清单写 `exe=xxx.exe`，磁盘上是无后缀 ELF 是正常的。** UNIX 下若同目录
   有同名无后缀文件就优先用它，这样一份清单能跨 Windows/Linux 使用。
3. **不要只传 PE 文件。** 从 Windows 整包上传会把 `xxx.exe`（PE）也带过去；
   若目录里只有 PE 而没有无后缀 ELF，宿主执行它会得到退出码 127。
   日志里 `exe=.../.run/xxx.exe` 且随后立即退出，基本就是这个原因。
4. **改了 `common/upluginguard.pas`（守卫/口令）必须宿主和所有插件一起重编**，
   否则"令牌对不上"。只改 `upluginproc.pas` 的复制逻辑则只需重编宿主。
5. **替换宿主 exe 后必须重启宿主进程**。磁盘文件换了，运行中的旧进程仍用旧代码。
6. 证书路径要写 `/` 分隔的 Linux 实际路径；Windows 反斜杠路径会被解析到
   `/home/cert-ca/...` 之类不存在的位置，宿主自动回退 HTTP。用 `http://` 访问
   或把证书放到正确位置。
7. `sh xxx.sh` 在 `/bin/sh=dash` 的机器上曾触发 `Bad substitution`；向导模板
   和活跃脚本已加"非 bash 则用 bash 重新执行自己"的保护。

## 6. 排障速查

| 现象 | 优先检查 |
| --- | --- |
| 发现插件 0 个 / 少一个 | 清单是否在 `GRoot` 的**直接**子目录；文件名是否 `*.plugin.ini`；name 是否重复；宿主是否还是旧 `ExeRoot` 层次 |
| 日志"插件 exe 不存在" | 清单 `exe=` 路径；Linux 下无后缀 ELF 是否存在；大小写（Linux 区分） |
| 退出码 127 | `.run` 副本是否 755；是否误把 Windows PE 当插件执行 |
| 退出码 3 / 提示"请从主程序进入" | 插件被手工双击（守卫 `missing`）或令牌过期/不匹配；这是守卫的正常行为，不是宿主拉起失败 |
| 菜单没有图标 | `icon=` 路径；图标文件是否随部署上传 |
| 插件页白屏 | `lw/` 静态资源（含 `.run/lw/`）；浏览器控制台 404 |
| 日志有插件就绪但页面连不上 | 是否用 `https://` 访问了实际回退到 HTTP 的宿主；端口是否被旧进程占用 |
